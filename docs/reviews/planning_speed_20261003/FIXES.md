# 2026-10-03 规划 CPU 处理优化

已实现并启用：场景点云体素化结果在同一画面内复用，候选几何检查采用 2 个工作线程。仅重启了空闲的远程规划节点，没有重启执行器、MoveIt、控制器或相机，也没有发送机器人/夹爪动作。新规划进程 PID 2227718；运行参数 planning.geometry_workers=2 已读取确认。

## 改动与精度约束

- PreparedGraspScene 按原来的 3 mm 算法体素化并保存只读副本。原来每个候选都会重复处理约 2.9 万个场景点，现在每个捕获画面仅预处理一次。没有跨画面缓存，执行前新画面的复核仍然重新计算。
- 仅把无 ROS 调用的接触测量、夹爪居中和点云碰撞判断放入工作线程。每个线程最多一个在途候选；上限 4，默认 2；按原输入顺序取结果，先完成的线程不能抢先选中低优先级候选。
- 候选排序、开爪及闭爪扫掠碰撞、接触深度、规划预算、FK 终点检查、执行前复核、轨迹速度和真实夹爪控制均保留。
- 取消或预算到期停止提交工作；工作线程异常向上传播，不能默认为可抓。运行中工作结束后才释放本次场景。
- planning.geometry_workers=1 可关闭线程并行，同时保留一次预处理的收益。默认 2 是保守的本机实测选择，4–8 个线程没有稳定额外收益。

## 完整候选准备回放

回放使用三份真实同步 RGB-D 图像、原始 SAM 掩码和记录的相机变换。桩规划器拒绝每个候选，使原生和几何两阶段都完整经过检查。逐项比较所有通过几何检查的候选顺序、各段位姿与预计夹爪开度，全部相同。下表只统计候选准备，不包含真实 IK、MoveIt 路径规划、网络或机械臂运动。

|历史画面|原实现|复用预处理 + 2 线程|加速比|进入规划的候选数|
|---|---:|---:|---:|---:|
|20261003_165902_803341|1.095 s|0.129 s|8.48 倍|65|
|20261003_170234_987941|1.016 s|0.124 s|8.17 倍|70|
|20261003_170536_818755|1.947 s|0.245 s|7.96 倍|95|

主要收益来自消除重复预处理。复用预处理后，串行和 2 线程之间的区别仅为几毫秒至十几毫秒，不应把全部收益归因于多核。

原始数据：integrated_geometry_replay.json。更小的 112 个提案基准见 geometry_benchmark.json，比较 1/2/4/8 线程和有无预处理；该微基准不等于完整规划耗时。

## 为什么 IK 还没有直接变成四倍快

同一真实 /compute_ik 服务，用一个不可达目标提交四次请求：串行两轮分别 0.4063/0.4056 s；同时提交两轮分别 0.4024/0.4023 s，均返回 NO_IK_SOLUTION。没有任何控制器动作或场景更新。此结果证明对当前服务仅增加客户端线程没有实质提速，不能根据 CPU 核数推断规划加速倍数。

[MoveIt Humble 官方运动学服务实现](https://github.com/moveit/moveit2/blob/humble/moveit_ros/move_group/src/default_capabilities/kinematics_service_capability.cpp) 的默认服务没有显式提供独立可重入回调组。该源代码与实测排队行为相符；本次没有改动已运行的 MoveIt 服务和 KDL 求解器的线程模型。

要进一步并行 IK，应在服务端提供独立求解器实例、明确的场景快照和夹爪状态，并对通过 IK 的解继续做完整路径及 FK 检查。不能让多个线程共用当前 planner 的 deadline、起始状态、预计夹爪开度、退避位姿和 last_solution_seed，然后任取最先完成的轨迹。

这次完整候选准备节省约 0.9–1.7 s。真实整次抓取收益需要新任务日志确认，尤其在原生候选用满固定阶段预算时，释放出的时间也可能用于尝试更多候选。此前审查估计的慢任务可省 10–18 s 是多项规划优化的合计目标，本次不能声称已实现该收益。当前纯放置流程不经过抓取候选几何检查，因此不能声称这项改动已经消除了放置 IK 延迟。
