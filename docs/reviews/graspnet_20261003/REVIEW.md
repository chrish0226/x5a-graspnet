# GraspNet 抓取精度代码审查（2026-10-03）

结论：当前链路存在能够造成抓偏、抓空和方向不匹配的代码缺陷。优先处理目标归属、模型抓入深度与真实夹爪几何的映射、改姿态后重新验证；现有日志不能支持“只是模型精度不足”的判断。

## 审查范围与证据

- 本地：`src/x5a_remote_grasp`、官方轨迹适配器、手眼标定配置、URDF、保存的 RGB-D 快照与 `logs/stack/remote_grasp.log`。
- 云端：只读取得当前 `/home/gjj/graspnet-baseline/grasp_server.py`，审查了服务器实际使用的 `models/graspnet.py` 和 `utils/collision_detector.py`。服务器文件两次 SHA256 一致：`07bfd5578eb18fa28b1f0faf50607098c8d18f1bab394abb35dc4fe0ef3c27e9`。本目录 `grasp_server.snapshot.py` 是审查时的副本。
- 将两帧保存图像重新提交给已有 SAM 分割服务。分数分别与历史响应一致；按相同的 8 像素膨胀和深度范围重建后，点数精确匹配历史 GraspNet 响应（3238、3288）。没有调用 ROS action、执行器或机械臂控制；没有更改运行配置或生产源码。
- CPU 离线复现：`reproduce.py`；数据结果：`evidence.json`；SAM 响应：`sam_replay.json`。运行方式：`/usr/bin/python3 docs/reviews/graspnet_20261003/reproduce.py`。
- 原有测试 `PYTHONPATH=src/x5a_remote_grasp /usr/bin/python3 -m pytest src/x5a_remote_grasp/test -q`：13 passed。这些测试未覆盖本次发现的推理后处理和姿态降级缺陷。

## 1. P1：改了预测姿态，却没有重算抓取有效性；高分候选的模板先于其他原生候选

位置：`remote_grasp_node.py:490-509, 1273-1310, 1335-1366, 1425-1448, 1590-1615`。

开度审计针对原始 GraspNet 闭合轴进行。随后 `_orientation_variants()` 加入基于目标相对机械臂方位、固定 roll 与 pitch/yaw 阶梯生成的姿态；`_select_candidate()` 对新姿态只检查工作区、IK 和 MoveIt 规划，没有对目标点云重查接触、开度或碰撞。原始 score/width/required_opening 被沿用，最终日志仍称其为 `selected GraspNet pose`。

物体同一位置绕不同轴夹持，所需开度和接触点都可能变化。例如沿盒子短边可夹，转到长边可能超过 88mm。IK 有解不能证明能抓住物体。外层先遍历候选、内层遍历该候选全部姿态，会先采用候选 #0 的未经评估模板，即使 #1 原始位姿可抓。

实证：`20261003_130521_424692` 最后采用 #0 的 reachable 姿态；对称夹爪闭合轴方向差约 **49.43°**。12:43 的橙块成功请求采用的是 **centroid template**，并非原始 GraspNet 位姿。13:03、13:05、13:07 日志均出现实际采用 reachable 的记录。

建议：先尝试所有合格原生候选；只有几何等价的夹爪对称变换可直接复用评估。非等价姿态必须用目标点云、实际夹爪几何重新验证和排序，标记独立来源，不复用模型分数作为新姿态质量。

## 2. P1：模型输出 depth_m 与指尖/TCP 映射脱节

位置：`geometry.py:17-28, 75-111, 251-292`；`remote_grasp_node.py:1348-1366`；配置 `remote_grasp.yaml:70,104`。

`depth_m` 被解析保存，但不参与候选位姿、TCP 映射和抓入距离计算。云端实际解码器选择 10/20/30/40mm 深度。官方碰撞模型中的手指前端在抓取坐标 `x=depth`，手指体积为 `depth-finger_length < x < depth`，不是把 translation 本身当指尖。

当前配置把 tool0 置于 translation 的 -X 15mm，并假定实际指尖在 tool0 前方约 15mm，等效指尖停在 translation，未体现模型选定的抓入深度。两帧实际候选深度为 20/30mm，却统一使用固定偏移。模型验证的抓取几何与真机实施的几何因此不一致，可能出现厘米级接触高度/侧向抓入差异。

建议：明确真实 tool0、指尖、指垫中心的几何关系，以模型原点与 depth 联合计算实际夹爪位姿，并用实际夹爪重新校验。这里是**确定的几何映射缺失**；每次真机偏差的精确数值仍需机械尺寸/实测确认。不要把 depth 直接叠加到现有真机参数上未经验证执行。

官方依据：[解码器](https://github.com/graspnet/graspnet-baseline/blob/main/models/graspnet.py)、[碰撞模型](https://github.com/graspnet/graspnet-baseline/blob/main/utils/collision_detector.py)、[夹爪几何](https://github.com/graspnet/graspnetAPI/blob/master/graspnetAPI/utils/utils.py)。

## 3. P1：膨胀掩码引入背景候选，目标归属过滤未实现

位置：云端快照 `grasp_server.snapshot.py:223-247, 368-374, 445, 488-489`；本地配置 `remote_grasp.yaml:9,15`。

原始 SAM 掩码向外膨胀 8 像素后，全部有效点都进入模型采样。`target_distance_thresh` 虽有配置和请求字段，但未被使用，响应明确返回 `target_distance_thresh_applied:false`。没有强制候选种子属于原始目标，也没有验证闭合区域有目标点。因此桌面边缘/背景种子可以成为返回候选。

实证（保留上下文点本身不一定错误，缺少目标归属约束才是缺陷）：

| 快照 | 原始目标有效点 | 推理有效点 | 原掩码外点比例 | 返回候选投影在原掩码外 |
| --- | ---: | ---: | ---: | ---: |
| 20261003_124328_379018 | 1921 | 3238 | 40.67% | 2/5 |
| 20261003_130521_424692 | 2022 | 3288 | 38.50% | 3/5 |

掩码外点的 base z 中位数分别约 7.6/8.3mm，明显偏向低处背景。投影在掩码外不能单独证明每个候选失败，但证明该路径没有把候选限定到识别目标。

建议：分开推理上下文点云和目标归属点云；基于原始/适度内缩目标掩码限制种子与接触区域，再检查闭合体积包含目标点。仅调小膨胀值不能替代归属验证。

## 4. P1：碰撞检查只看目标，且异常会静默绕过；没有排除空抓

位置：云端快照 `grasp_server.snapshot.py:229-231, 256-262`；本地 `remote_grasp_node.py:1766-1784`。

`cloud_collision` 只来自目标原始掩码，遗漏桌面、邻近物体和其他场景障碍；MoveIt 补充的只是固定桌面和相机。云端 `except Exception: pass` 会在碰撞检查失效时继续返回候选。调用没有启用 `return_empty_grasp`，也没有等价的“夹爪闭合区有目标点”检查。碰不到目标不等于成功抓住目标。

此外，云端沿用官方固定手指长 60mm、厚 10mm、高度由候选给出（解码为 20mm）的模型，未针对 X5A 夹爪几何校准；不能把云端通过视为真实夹爪碰撞已通过。`collision_thresh=0.01` 是体素占据比例阈值，**不是容许穿透 1cm**，旧记忆对此的解释不正确。

建议：使用完整有效场景/局部场景点云检查手指和接近扫掠，使用目标点云单独检查夹持占据/接触；异常明确返回失败或降级状态。替换为实测夹爪几何。官方实现支持 empty-grasp 检查：[碰撞检测实现](https://github.com/graspnet/graspnet-baseline/blob/main/utils/collision_detector.py)。

## 5. P1：平移距离去重误删不同抓取方向，top-k 后才做关键审计

位置：云端快照 `grasp_server.snapshot.py:265-273`；本地 `remote_grasp_node.py:1273-1303`。

云端仅按 translation 的 20mm 距离去重，不比较旋转角。位于同一区域但闭合轴不同的可行候选被删除；对约 3cm 的方块尤其容易只留下边缘位置。开度和中心带审计在 top-k 返回之后才进行，返回候选可能全部被拒，而被提前删除/截断的原生候选没机会接受规划。

离线反例：位置相同、方向差 90° 的两个候选仅保留一个。官方 `GraspGroup.nms()` 同时提供平移与旋转阈值：[官方 NMS 接口](https://github.com/graspnet/graspnetAPI/blob/master/graspnetAPI/grasp.py)。

建议：按平移和旋转（考虑平行夹爪对称性）共同去重；完成目标归属、几何有效性筛选后再截断，保留方向多样性。增加 top_k 本身不能恢复已被去重删除的候选。

## 6. P2：开度审计只量跨度，没有检查候选是否居中

位置：云端快照 `grasp_server.snapshot.py:276-298`。

`np.ptp()` 只计算物体跨度，没有检查它相对当前夹爪中心的偏移。闭合轴上点分布为 +10～+70mm 时，返回需开度 60mm；固定在当前中心的对称夹爪实际需开到至少 140mm。代码没有同时把抓取中心移动到 +40mm，60mm 结论会放过偏心候选。

另一个问题：走廊仅限制 approach 轴 ±50mm，不限制夹爪高度方向，也不使用 depth 定义的手指范围。高处或不在实际手指扫掠区的点可能使审计误拒；稀疏目标返回 None 又完全跳过审计。

建议：在实际接近/闭合体积内计算闭合轴两侧边界与中心偏移，使用稳健分位数与点数/覆盖置信度。居中校正会改几何，必须重新检查碰撞。

## 7. P2：相机 Z 分位数不能直接代表 base Z 高度带

位置：云端快照 `grasp_server.snapshot.py:232-238`；本地 `remote_grasp_node.py:838-850,1292-1302,1323-1329`。

服务器把真实点云压缩成“相同平均 x/y + z 的两个分位数端点”。本地转换这两个虚构点得到高度带，并据此拒绝候选、修改质心抓取高度。斜视时 base z 同时依赖 camera x/y/z，丢掉 x/y 与深度的对应关系后，排序两个端点不能修复。

离线反例：使用当前标定矩阵，一个厚度为 0、base z 恒定的 8×12cm 水平面，被计算出 **22.54mm** 的高度带。两帧实际带下界分别比完整原掩码点云变换后的 p5 高约 **4.0/3.7mm**，相对于 7mm 的中心带余量已经显著。这也意味着新放置公式 `center+abs(Rzz)*delta_cam_z` 仍是近似，不能声称对任意视角都准确。

建议：对每个有效目标点做完整 TF 后，直接统计 base z 和接触区域几何；通过平面/物体结构估计抓取高度，避免用相机深度跨度代替物体真实高度。

## 8. P1（执行结果）：空闭合也会报告 holding=true

位置：`remote_grasp_executor.py:448-452,504-528`；`official_trajectory_adapter.py:431-456`。

适配器对闭合目标无条件返回 reached_goal=True；执行器随即把 holding 标为 True，没有检查闭合后爪间隙、接触状态或提起后的目标变化。因此夹空也可能显示“抓取完成”。这不是模型偏差的起因，却会掩盖失败并污染成功率判断。

建议：把“闭合动作完成”和“确认持物”分开，结合爪间隙、状态是否新鲜、提起后的视觉变化判断，无法确认时返回 unknown。不要把模型分数解释为抓取成功概率。

## 其他已确认缺陷与限制

- **兜底失败时反馈类型断言**：`remote_grasp_node.py:1576` 把 None 候选编码为 -1，再赋给 uint32 的 `candidate_index`（接口文件与 `_feedback:529`）。今天 13:04 日志已经出现 AssertionError 并导致 goal 异常终止，失败报告因此丢失。这不是位置精度问题，但解释了部分请求为什么直接失败。
- **低分兜底无限放行**：`min_score=0`。今天实际采用过 score≈0.288、0.216 的改姿态候选。阈值应通过离线和真机结果校准，不能随意宣称 0.5 是通用门槛。
- **抓取终点精度未单独保证**：`moveit_plan.py:363-369` 接受 fraction≥0.95 的未完整笛卡尔轨迹，没有验末端是否到目标；适配器按关节误差 0.02rad 判完成，没有最终 TCP 检查。对窄接触带，这可能贡献毫米级误差，但尚未找到某次抓偏与之直接对应的记录。
- **没有临近抓取的视觉复核**：只在请求开始检查帧新鲜度；云端推理、定位、规划后不复核目标移动，执行器允许接收后的计划保留 180s。物体被推动、手进入场景或目标移动时，原抓取点不会更新。
- **随机性缺乏可重放记录**：每次 default_rng() 不设/记录种子，小物体仅两三千点却重复采样到 20000；上游 FPS/局部采样的具体抖动幅度未进行重复 GraspNet 推理基准，不能量化为已证实主因。
- **简单 /grasp 的颜色分支有布尔掩码错误**：云端快照 `:185-188` 已把 mask 转为 0/1，却用 `m>127` 取图像，得到空集合与 NaN。当前 /v1/grasp 传 color=None，通常不触发，不列为当前抓偏主因。
- 本地当前源码和 build 节点 SHA256 一致。13:06 快照与日志已有新放置高度公式和成功的 place-only 规划，修复已进入后续运行；这些证据不证明真机叠放成功。
- 手眼标定误差是同一批训练样本上的 3.76mm 均值、8.40mm 最大值，holdout 为 0，并有运动轴平行警告。可作为误差量级线索，不能替代独立多点真机精度验证。没有重新测量 TCP，也没有评估模型 checkpoint 在当前物体上的泛化。

## 建议修复与验证顺序

1. 限定目标归属，恢复旋转敏感去重，先评估全部原生候选。
2. 明确 depth/TCP/实际手指模型关系；改姿态必须重新做目标接触与完整场景碰撞评估。
3. 修正基于完整 base 点云的高度和偏心开度检查。
4. 区分闭合完成与持物确认，补兜底错误反馈。
5. 固定保存的 RGB-D 帧做重复推理，记录原生/改姿态/质心三类结果和拒绝原因；通过规划后，以用户操作的真机多点测试测量 XY、高度、角度偏差和真实成功率。

以上为审查和复现结果，生产实现尚未修复。硬件误差与模型本身泛化误差需要在软件几何一致后单独测量。
